🔴 C-01 — Глобальний singleton TelegramClient (telegram-bot/main.py, рядок 45)
Проблема: Єдиний TelegramClient обслуговує всіх користувачів. Якщо навіть двоє людей одночасно намагаються авторизуватись — вони перезаписують сесії один одного. Бот фізично не може обслуговувати більше одного акаунту Telegram.

# ЗАРАЗ (небезпечно)
client = TelegramClient(SESSION_FILE, API_ID, API_HASH)
# ЯК МАЄ БУТИ
clients: dict[str, TelegramClient] = {}
Як виправити: Ввести SessionManager — словник клієнтів з ключем phone або user_id.

🔴 C-02 — Гонка даних у авторизаційному флоу (main.py, рядки 57–58, 131)
Проблема: pending_code_hash: dict = {} зберігається глобально. При паралельних запитах send_code для різних номерів — client (singleton) "чекає" код лише для останнього телефону, тоді як хеш першого вже в словнику. Верифікація першого номера підпишеться під другого клієнта.

Як виправити: Кожен TelegramClient мусить мати власний phone_code_hash, прив'язаний до сесії.

🔴 C-03 — Відсутня автентифікація на всіх ендпоінтах FastAPI (main.py)
Проблема: Будь-хто, хто знає IP і порт (8001) сервера, може викликати /groups/join, /campaigns/start, /parse/members тощо — без жодного пароля чи токена. Це означає, що хтось може:

надіслати тисячі повідомлень від імені жертви
парсити учасників чужих груп
вступати у будь-які групи
Як виправити: Додати middleware з перевіркою X-API-Key або Authorization: Bearer <secret>.

🔴 C-04 — get_entity(int(id)) падає для невідомих сутностей (main.py, рядок 281)
Проблема: Telethon не може отримати ентіті за числовим ID, якщо вона не в кеші діалогів клієнта. Це означає, що автовступ до груп, які бот ще не "бачив", буде постійно падати з ValueError.

# Рядок 281 — ПАДАЄ для нових груп
entity = await client.get_entity(int(group.telegramId))
Як виправити: Спочатку завжди пробувати через username, і лише якщо його немає — через InputPeerChannel з access_hash.

🔴 C-05 — Дублювання записів у таблиці jobs (api-server/routes/groups.ts, рядок 131)
Проблема: Ендпоінт /groups/join-status при кожному виклику робить INSERT у таблицю jobsTable. Якщо Python-сервіс відправляє повторні статуси або відбувається retry — в БД з'являються десятки дублікатів одного і того ж job.

Як виправити: Замінити INSERT на INSERT ... ON CONFLICT DO UPDATE або UPSERT.

🟠 B-01 — Кампанія позначається active навіть якщо Python-сервіс недоступний (campaigns.ts, рядки 141–143)
Проблема: При запуску кампанії Node.js спочатку оновлює статус у БД на active, а потім намагається повідомити Python-сервіс. Якщо Python недоступний — кампанія назавжди "застряє" в active без реального виконання.

Як виправити: Спочатку перевіряти доступність Python-сервісу, і лише при підтвердженні — оновлювати статус у БД.

🟠 B-02 — NaN при парсингу ID кампаній/груп (campaigns.ts та groups.ts)
Проблема: parseInt(req.params["id"]!) без перевірки на NaN. Якщо хтось передасть /api/campaigns/abc — запит до БД відправляється з NaN, що призводить до непередбачуваної поведінки або помилок Drizzle.

// ЗАРАЗ (небезпечно)
const id = parseInt(req.params["id"]!);
// ЯК МАЄ БУТИ
const id = parseInt(req.params["id"]!);
if (isNaN(id)) return res.status(400).json({ error: "Invalid ID" });
🟠 B-03 — Фільтрація контактів в пам'яті Node.js (contacts.ts, рядки 11–23)
Проблема: Всі контакти завантажуються з БД у пам'ять Node.js, і лише потім фільтруються. При базі 100 000+ контактів — OOM або критичне гальмування сервісу.

Як виправити: Перенести фільтрацію у WHERE-clause SQL запиту.

🟠 B-04 — Таймаут 3 хвилини при парсингу vs реальний таймаут проксі (parse.ts, рядок 18)
Проблема: AbortSignal.timeout(180000) встановлює 3-хвилинний таймаут для парсингу учасників. Але HTTP-проксі (Nginx/Replit) зазвичай має таймаут 60с. Результат — клієнт отримує 504 Gateway Timeout, хоча Python продовжує працювати у фоні.

🟠 B-05 — Race condition при ініціалізації AuthModal (auth-modal.tsx, рядки 154–167)
Проблема: Два useEffect конкурують за встановлення кроку авторизації: один чекає authStatus з API (може тривати >4с), другий через setTimeout(4000) форсово переходить на крок "phone". Результат — авторизований користувач може бути переведений на форму входу.

🟠 B-06 — API ID/Hash вводяться у UI але не зберігаються на сервері (auth-modal.tsx, рядки 377–382)
Проблема: Кроки "apiid" та "apihash" збирають значення від користувача, але коли потім викликається send-code, ці значення нікуди не передаються. Бекенд читає TELEGRAM_API_ID і TELEGRAM_API_HASH виключно з env-змінних — UI-поля для цих даних є нефункціональними.

Як виправити: Або видалити ці кроки з UI (якщо env вже налаштовані), або додати ендпоінт POST /auth/set-credentials для динамічного оновлення конфігурації.

🟠 B-07 — FloodWait пропускає групу замість retry (main.py, рядки 295–298)
Проблема: При FloodWaitError бот спить потрібний час, але після пробудження просто переходить до наступної групи — та, що викликала FloodWait, так і не обробляється.

🟠 B-08 — confirm() для підтвердження видалення кампанії (campaigns.tsx, рядок 77)
Проблема: Нативний window.confirm() блокується більшістю браузерів у контексті iframe/proxy (саме в такому середовищі Replit). Видалення або відбувається без підтвердження або взагалі не відбувається.

Як виправити: Замінити на компонент AlertDialog з shadcn/ui (вже підключений до проекту).

🟠 B-09 — Статус failed груп не синхронізується (groups.ts → main.py)
Проблема: Якщо callback від Python-сервісу до Node API недоступний (req.log.warn на групі 305–312), база залишається в стані pending назавжди. Немає механізму повторних спроб або TTL для "зависання".

🟠 B-10 — Вкладені FormField з однаковим іменем (campaign-form.tsx, рядки 241–262)
Проблема: react-hook-form не підтримує вкладені <FormField name="targetGroupIds"> в циклі. Це призводить до десинхронізації стану між дочірніми полями та реальним значенням масиву.

ЧАСТИНА IV — РОЗБІЖНОСТІ ТИПІВ (P2)
═══════════════════════════════════════
🟡 T-01 — AuthStatus не включає поле id (Telegram user ID)
Python повертає "id": me.id, але AuthStatus в spec і TypeScript-типах не має цього поля. Поле ігнорується.

🟡 T-02 — UpdateCampaignBody.status і scheduleType — string, але Campaign використовує enum
При передачі даних кампанії до update-мутації TypeScript вимагає кастинг через as any або as CampaignStatus — що є симптомом невідповідності схем.

🟡 T-03 — TelegramGroup.type — enum, але Group.type — string
Два різних типи для одного концепту в одній специфікації. Призводить до as any на фронтенді.

🟡 T-04 — telegramId в GroupInfo — string, але Telegram IDs — числа
Python-код робить int(group.telegramId) (рядок 281), що падає якщо рядок не числовий. Поле має бути або int в Pydantic, або валідуватись.

🟡 T-05 — targetGroupIds можуть повернутись як null з БД
Якщо стовпець targetGroupIds в БД зберігається як JSON і запис пошкоджений — фронтенд отримає null замість [], що викличе TypeError: Cannot read properties of null (reading 'map').

🟡 T-06 — Відсутні enum типи для Group.status у формах редагування
GroupStatus визначений у схемах, але UI-форми просто передають рядкові значення без перевірки.

ЧАСТИНА VII — НЕРЕАЛІСТИЧНИЙ ФУНКЦІОНАЛ
═══════════════════════════════════════
🔴 NF-01 — Кроки введення API ID та API Hash в AuthModal — повністю нефункціональні
UI збирає apiId і apiHash від користувача через красиві форми, але ці значення ніколи не передаються на сервер. Бекенд читає TELEGRAM_API_ID/TELEGRAM_API_HASH виключно з env. Це імітація функціоналу.

🟠 NF-02 — Налаштування розкладу кампанії "custom" без валідації
При виборі "custom" інтервал (intervalHours) є необов'язковим у Zod-схемі. Користувач може відправити кампанію без інтервалу — Python падає до дефолту 1 годину без попередження.

🟠 NF-03 — Зупинка кампанії (pause) не скасовує активні задачі в Python
PATCH /api/campaigns/:id/pause оновлює статус у БД, але не сигналізує Python-планувальнику зупинити поточне виконання. Кампанія "призупинена" у БД, але продовжує відправляти повідомлення.

🟠 NF-04 — Кампанії не відновлюються після перезапуску сервісу
APScheduler налаштований in-memory. При рестарті Python-сервісу всі active кампанії залишаються active у БД, але планувальник про них не знає — вони ніколи не запускаються.

ЧАСТИНА VIII — ЯКІСТЬ КОДУ ТА АРХІТЕКТУРА
═══════════════════════════════════════
🟡 A-01 — PYTHON_SERVICE_URL захардкоджено у 6+ файлах
Кожен route-файл Node.js має власну копію:

const PYTHON_SERVICE_URL = process.env["PYTHON_SERVICE_URL"] || "http://localhost:8001";
Має бути централізовано в config.ts.

🟡 A-02 — Відсутня централізована обробка помилок в Express
Немає app.use((err, req, res, next) => {...}) — всі помилки обробляються локально в кожному обробнику по-різному.

🟡 A-03 — DeprecationWarning в FastAPI (on_event)
Python логи одразу при старті показують:

DeprecationWarning: on_event is deprecated, use lifespan event handlers instead.
Рядки 554 та 569. Треба мігрувати на @asynccontextmanager lifespan.

🟡 A-04 — scheduler не зберігає стан між перезапусками
AsyncIOScheduler з APScheduler використовується без jobstores (persistent storage). Всі заплановані задачі губляться при рестарті.

🟡 A-05 — Відсутні індекси на таблицях БД
jobsTable, groupsTable не мають індексів на status, campaignId, createdAt — повільні запити при зростанні даних.

ЗАГАЛЬНИЙ ВИСНОВОК
═══════════════════════════════════════
Проект Group Agent має добре побудований UI та загальну архітектурну концепцію, однак містить ряд фундаментальних проблем, які роблять його непридатним для production-використання в поточному стані.

Найкритичніші проблеми:

Архітектурна: Singleton TelegramClient робить систему однокористувацькою за замовчуванням і схильною до race conditions при будь-якому паралельному використанні.
Безпекова: Відсутність автентифікації на API-рівні — будь-хто з доступом до мережі може керувати чужим Telegram-акаунтом.
Функціональна: Кроки введення API ID/Hash у UI — декоративні, дані нікуди не зберігаються. Пауза кампанії не зупиняє Python-планувальник. Кампанії не відновлюються після рестарту.
Надійності: Відсутні механізми retry для callbacks між сервісами, немає захисту від дублювання jobs, немає персистентного планувальника.
Масштабованості: Фільтрація контактів в Node.js-пам'яті, відсутність пагінації, відсутність індексів БД.
Позитивне: Якість UI-компонентів висока, типізація через OpenAPI + Orval — правильний підхід, розподіл на Node.js (оркестрація) + Python (Telegram-логіка) — архітектурно виправданий.
